01 · Cómo se aplica

ACID en mi base de datos Las cuatro garantías las sostiene el motor, no el código de la aplicación.

✅ Sí se aplica, y correctamente. Cada letra está cubierta por un objeto concreto del proyecto y comprobada por pruebas.
A · Atomicidad
Código
-- database.transaccion(): una conexión dedicada
BEGIN  ->  ...sentencias...  ->  COMMIT
                      (si algo falla ->  ROLLBACK)
Lo que digo
Un procedimiento como sp_crear_partida_completa hace dos inserciones y, si una falla, PostgreSQL revierte las dos: o todo, o nada. Eso lo garantiza la transacción, que se ejecuta sobre una conexión dedicada (BEGIN → COMMIT / ROLLBACK).
C · Consistencia
Código
CONSTRAINT fk_historial_usuario
  FOREIGN KEY (id_usuario) REFERENCES usuarios (id);
CHECK (correo ~* '^[^@\s]+@[^@\s]+\.[^@\s]+$')
Lo que digo
La base impone las reglas: clave foránea del historial hacia usuarios, UNIQUE de usuario/correo, y un CHECK con forma de correo. Por eso un resultado para un usuario inexistente se rechaza (error de clave foránea).
I · Aislamiento
Código
... FOR UPDATE;   -- bloquea la fila mientras dura la transacción
Lo que digo
Con SELECT ... FOR UPDATE dos operaciones concurrentes sobre la misma partida no se pisan, y un código de verificación no se puede usar dos veces. Se usa al leer-modificar-guardar la partida y en fn_confirmar_codigo.
D · Durabilidad
Código
SELECT estado_json FROM partidas WHERE id = ?;
Lo que digo
La escritura se confirma en disco (WAL) y la lectura vuelve a la tabla, no a un caché en memoria. Por eso una partida sigue existiendo después de reiniciar el servidor.
02 · Cómo aplica

CAP en mi proyecto El teorema describe sistemas distribuidos con réplicas.

✅ CAP no se “aplica” porque no corresponde: el proyecto es un sistema CA, y eso no es un defecto.
El tipo de sistema
Lo que digo
Memoria Ninja es un monolito: un servidor Node.js y una sola instancia de PostgreSQL, sin réplicas. La P de CAP (tolerancia a particiones) describe cortes de red entre nodos que replican datos; al haber un solo nodo, esa partición no existe.
Por qué no hay disyuntiva
Lo que digo
Como no hay réplicas, no hay que elegir entre consistencia y disponibilidad: el sistema es consistente (ACID del punto 1) y disponible mientras el nodo esté en pie. Recién si algún día agrego réplicas distribuidas, el teorema empezaría a aplicar.
03 · Abstracción de lectura

Las 4 vistas JOIN, GROUP BY y los cálculos viven en PostgreSQL, no en el código.

El backend solo hace SELECT * FROM <vista>. La lógica relacional queda definida una sola vez en la base.

Vista 1 · vw_partidas_recientes
Código
CREATE OR REPLACE VIEW vw_partidas_recientes AS
SELECT id, creada_en, actualizada_en
FROM partidas
ORDER BY actualizada_en DESC, creada_en DESC;
Lo que digo
Muestra las partidas ordenadas por la más reciente. Es la vista que aprovecha el trigger del punto 5: actualizada_en la llena el trigger, y acá se usa para ordenar.
Vista 2 · vw_historial_detallado
Código
CREATE OR REPLACE VIEW vw_historial_detallado AS
SELECT h.id, h.id_usuario, u.usuario, h.id_partida,
       h.zona, h.puntaje, h.modo, h.ganador, h.jugada_en
FROM historial_partidas h
LEFT JOIN usuarios u ON u.id = h.id_usuario
ORDER BY h.jugada_en DESC;
Lo que digo
El historial guarda el id_usuario, pero para mostrar el nombre del jugador hay que cruzar con la tabla usuarios. Ese JOIN lo resuelve la vista; el backend ya recibe el nombre listo.
Vista 3 · vw_ranking_mejor_puntaje
Código
CREATE OR REPLACE VIEW vw_ranking_mejor_puntaje AS
SELECT u.id AS id_usuario, u.usuario,
       MAX(h.puntaje)  AS mejor_puntaje,
       COUNT(h.id)     AS total_partidas,
       MAX(h.jugada_en)AS ultima_jugada
FROM historial_partidas h
INNER JOIN usuarios u ON u.id = h.id_usuario
GROUP BY u.id, u.usuario
ORDER BY mejor_puntaje DESC;
Lo que digo
Es el ranking. Con MAX saco el mejor puntaje y con COUNT cuántas partidas jugó; GROUP BY agrupa por usuario. Toda la estadística la calcula la base, no el código de Node.
Vista 4 · vw_usuarios_resumen
Código
CREATE OR REPLACE VIEW vw_usuarios_resumen AS
SELECT u.id, u.usuario, u.correo, u.nacimiento, u.creado_en,
       COUNT(h.id) AS total_partidas,
       MAX(h.puntaje) FILTER (WHERE h.puntaje IS NOT NULL) AS max_puntaje,
       MAX(h.jugada_en) AS ultima_partida
FROM usuarios u
LEFT JOIN historial_partidas h ON h.id_usuario = u.id
GROUP BY u.id, u.usuario, u.correo, u.nacimiento, u.creado_en;
Lo que digo
Resume cada cuenta con sus estadísticas en una sola consulta. El FILTER (WHERE ...) calcula el máximo solo sobre puntajes no nulos, y el LEFT JOIN hace que también aparezcan los usuarios que todavía no jugaron.
04 · Escritura encapsulada

Los 2 procedimientos almacenados El backend los dispara con CALL; la lógica vive en el motor.

Procedimiento 1 · sp_registrar_partida
Código
CREATE OR REPLACE PROCEDURE sp_registrar_partida(
    p_id_usuario TEXT,
    p_zona       TEXT,
    p_puntaje    INTEGER,
    p_modo       TEXT,
    p_ganador    TEXT
)
LANGUAGE plpgsql AS $BODY$
BEGIN
    INSERT INTO historial_partidas
        (id, id_usuario, zona, puntaje, modo, ganador)
    VALUES (
        gen_random_uuid()::TEXT,
        p_id_usuario, p_zona, p_puntaje, p_modo, p_ganador
    );
END;
$BODY$;
Lo que digo
Recibe los 5 datos del resultado y guarda una fila en historial_partidas. gen_random_uuid() genera el id único del registro. En mi juego lo invoca el endpoint POST /api/procedimientos/registrar-partida con un CALL.
Procedimiento 2 · sp_crear_partida_completa
Código
CREATE OR REPLACE PROCEDURE sp_crear_partida_completa(
    p_id_partida  TEXT,
    p_estado_json TEXT,
    p_id_usuario  TEXT,
    p_zona        TEXT,
    p_puntaje     INTEGER,
    p_modo        TEXT,
    p_ganador     TEXT
)
LANGUAGE plpgsql AS $BODY$
BEGIN
    INSERT INTO historial_partidas
        (id, id_usuario, id_partida, zona, puntaje, modo, ganador)
    VALUES (
        gen_random_uuid()::TEXT,
        p_id_usuario, p_id_partida, p_zona, p_puntaje, p_modo, p_ganador
    );

    INSERT INTO partidas (id, estado_json)
    VALUES (p_id_partida, p_estado_json);
END;
$BODY$;
Lo que digo
Este hace dos inserciones en una sola operación: primero el resultado en historial_partidas (relacionado por id_partida) y después la partida con su estado_json (el tablero, cartas encontradas, etc.). Como es una sola operación, es atómico: o se guardan las dos, o ninguna.
Cómo se llaman: PostgreSQL prohíbe subconsultas como argumento de CALL, por eso en las demos van dentro de un bloque DO $$ ... $$ que primero resuelve el id del usuario y luego llama al procedimiento.
05 · Automatización

El trigger de la tabla partidas Recalcula la fecha de actualización solo, dentro de la base.

✅ Sí se aplica. El trigger se dispara en cada UPDATE real sobre partidas, sin que el backend lo tenga que hacer.
Parte 1 · La función
Código
CREATE OR REPLACE FUNCTION fn_partidas_actualizar_fecha()
RETURNS TRIGGER AS $$
BEGIN
    NEW.actualizada_en = now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
Lo que digo
Esta función es la que hace el trabajo. NEW es la fila que se está modificando y now() es la hora actual del servidor: le asignamos la fecha al campo actualizada_en y devolvemos la fila con RETURN NEW para que se guarde.
Parte 2 · El trigger que la engancha
Código
CREATE TRIGGER trg_partidas_actualizar_fecha
    BEFORE UPDATE ON partidas
    FOR EACH ROW EXECUTE FUNCTION fn_partidas_actualizar_fecha();
Lo que digo
BEFORE UPDATE significa que se ejecuta antes de cada modificación, y FOR EACH ROW que corre por cada fila afectada. Así, cada vez que se actualiza una partida, la fecha se refresca automáticamente.
Parte 3 · Cómo se demuestra
Código
UPDATE partidas SET estado_json = estado_json
 WHERE id = 'partida-demo';

SELECT id, creada_en, actualizada_en FROM partidas;
Lo que digo
Hago un UPDATE cualquiera y el SELECT muestra cómo actualizada_en cambió sola. El backend nunca escribió esa fecha: la puso el trigger.
